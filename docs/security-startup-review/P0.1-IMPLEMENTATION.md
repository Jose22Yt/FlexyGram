Proyecto FlexyGram 1.0, responsable @Lukhou23. Cambio limitado a registros y diagnósticos sobre `security/paso-3-p0-isolated-diagnostic`, derivada de `develop` en `28adb8174b859d8ce6d30c3f8d7629505b48a967`. Conserva créditos y licencias originales. No atribuye el incidente de sesiones/bots a estos hallazgos.

## Correcciones implementadas

Todos los archivos de producción siguientes están bajo `TMessagesProj/src/main/`:

| Archivo | Corrección |
| --- | --- |
| `java/org/telegram/messenger/AuthTokensHelper.java` | `saveLogInToken` registra solamente la operación; la carga fallida registra tipo de excepción, sin mensaje ni throwable. Serialización, preferencias, límites y solicitud de backup se conservan. |
| `java/org/telegram/messenger/PushListenerController.java` | Los fallos 2/3 conservan códigos y explicación, sin claves ni identificadores de claves. No se vuelca JSON ni excepción completa al fallar. El tipo remoto `loc_key`, de contenido arbitrario, se sustituye en logs por operaciones fijas. No cambian validación criptográfica, dispatch, esperas ni callbacks. |
| `java/org/telegram/messenger/GcmPushListenerService.java` | Registros de recepción y renovación sin token, mapa de datos ni remitente. El token y payload originales siguen llegando al controlador. |
| `java/org/telegram/messenger/GooglePushListenerServiceProvider.java` | Elimina token almacenado del diagnóstico privado. `lastError` conserva solo tipo, evitando reintroducir mensajes sensibles en otros consumidores. Mantiene éxito, error, reintento y registro originales. |
| `java/org/telegram/messenger/CaptchaController.java` | Sanea registros del bloque Recaptcha **ya comentado**, sin activarlo ni corregir su disponibilidad. `formatException` devuelve tipo en vez de texto arbitrario. Conserva el fallo de actividad existente y la entrega de resultados. No se ejecutó CAPTCHA real. |
| `java/org/telegram/messenger/FileLog.java` | Los dos volcados de protocolo conservan tipo de operación/objeto, tiempos, identificadores técnicos y código numérico de error; eliminan cuerpos de petición, respuesta, error y mensaje no analizado. Sin fallback a `toString`. Fallos de estos diagnósticos no imprimen throwable. Evita depender de listas incompletas de campos privados para OTP/contraseñas/tokens. No se desactiva el sistema global de logs. |
| `python/dev_server.py` | El token continúa escribiéndose en su archivo original, pero no se registra ni se revela la ruta. Errores de escritura, bind, depuración y desinstalación no interpolan valores externos/excepciones completas. Los informes de fallo de comandos/plugins son genéricos o conservan solo tipo; no incluyen mensajes arbitrarios. `handle_error` evita el traceback predeterminado de socketserver. Se conservan comparación de token, comandos, estados y respuestas de éxito. Los detalles textuales de los errores cambian deliberadamente. |
| `python/extera_utils/plugin_loader.py` | El límite de arranque del servidor registra tipo de excepción, no su mensaje. |
| `java/app/exteraless/plugins/PythonPluginsEngine.java` | El catch directamente relacionado con arranque del servidor registra operación y tipo, sin reenviar el throwable al informe de fallos. |

Los riesgos explícitos de tokens/claves provienen de la base heredada. Este PR introduce su corrección y pruebas; no cambia API ID/hash, identidad Android, respaldo de sesiones ni las otras áreas P0 pendientes. Los volcados RPC privados estaban condicionados por `DEBUG_PRIVATE_VERSION`; no se afirma que estuvieran activos en la APK anterior. La seguridad de los nuevos mensajes no depende de desactivar Debug, Staging, Release o sus logs.

## Pruebas reproducibles

Desde la raíz, sin instalar dependencias Python:

```sh
python -m unittest discover -s tests/security -v
git diff --check
```

`tests/security/test_p01_logs.py` y `java_harness.py` usan exclusivamente datos sintéticos, módulos falsos, memoria y archivos temporales. No abren sockets, no contactan Telegram/Firebase, no cargan plugins reales ni manipulan sesiones. El arnés requiere Java con compilador: `javac` o el módulo `jdk.compiler`; si falta, la prueba Java se marca omitida, no aprobada.

Resultados en esta implementación:

- **13 pruebas aprobadas, 0 fallidas, 0 omitidas.** Diez pruebas Python de ejecución, dos contratos estáticos y una prueba Java compuesta.
- Python: secreto ausente en mensajes enviados al puente Android, alternativa `stderr`, error de token/archivo, bind, debugger, excepciones de comandos, informes de plugins, entrada malformada y fallo no controlado del handler. Token escrito sin modificación; ping, rechazo de token incorrecto/ausente, aceptación correcta, dispatch y continuidad del stream comprobados.
- Java: compila completas `AuthTokensHelper`, `GcmPushListenerService`, `GooglePushListenerServiceProvider` y `CaptchaController` contra dobles mínimos de Android/Firebase/almacenamiento. Comprueba persistencia/lectura del token, solicitud de backup, entrega del token y payload a los callbacks, exclusión de push deshabilitado, fallos/éxito FCM, resultado CAPTCHA existente y entrega de resultado sintético. No equivale a verificar los servicios reales.
- Compila/ejecuta **los métodos de producción** `postProtocolDump`, `dumpResponseAndRequest` y `dumpUnparsedMessage` con colas y sumideros locales. Cuerpos con campos OTP/contraseña/token y un `toString` que falla no se serializan; se conserva `code=400`. Ejecuta los mensajes corregidos de error push, extraídos del código, con una excepción sintética. **No ejecuta descifrado push ni el controlador completo.**
- El arnés recorre las ocho combinaciones de `DEBUG_VERSION`, `LOGS_ENABLED` y `DEBUG_PRIVATE_VERSION`. Esto prueba las rutas del arnés con flags, **no compila tres variantes Android**. Verifica ausencia del canario en texto y hexadecimal en las salidas capturadas.
- Analiza la sintaxis Java de los siete archivos Java de producción modificados usando `JavacTask.parse`. No resuelve todos los tipos Android de los tres archivos grandes restantes.
- Sintaxis Python aprobada para ambos archivos de producción; `git diff --check` aprobado.
- Control negativo ejecutado contra los dos archivos Python originales de `28adb817…`: diez pruebas, **ocho fallos esperados por exposición**, cero errores de ejecución. Las mismas diez pasan tras el cambio.

Entorno efectivo: Python 3.12.14 y OpenJDK 17.0.20. Inicialmente faltaba el ejecutable `javac`; la instalación con apt no pudo completarse por permisos de caché. Se descargó un paquete JDK 17 de 71,6 MB fuera del repositorio, pero finalmente las comprobaciones utilizan el módulo `jdk.compiler` que ya estaba disponible en Java. Ninguna dependencia ni archivo Gradle del proyecto se modifica por ello.

## Límites y pendientes

- **No se ejecutó Gradle ni una compilación Android completa:** este entorno no tiene preparado el toolchain Android/JDK 21 del Paso 3. No se generó APK. La compilación parcial y el análisis sintáctico no prueban integración Android/Chaquopy, enlace nativo ni funcionamiento en dispositivo.
- No se ejecutó la batería general de plugins basada en pytest; el entorno no dispone de pytest. La batería nueva funciona con unittest estándar.
- No se probó Logcat real, escritura real de FileLog en Android, Crashlytics, notificaciones de Firebase ni reCAPTCHA remoto. Las pruebas verifican valores antes de entrar en los sumideros simulados y los métodos RPC indicados.
- No se modifica la API genérica de logging ni se promete sanear cualquier cadena que un plugin arbitrario decida registrar. Los cambios cubren los productores y sumideros directamente relacionados descritos arriba. No se ha demostrado una filtración consumada.
- No se borran registros antiguos ni se accede al teléfono; el parche evita nuevas emisiones en las rutas corregidas y no elimina copias previas.
- Siguen pendientes revisión del PR, compilación Android controlada sin uso personal y comprobaciones de integración offline antes de declarar cerrado P0.1 en dispositivo. Las pruebas autenticadas continúan bloqueadas por los demás P0.
